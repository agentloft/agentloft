# ADR-0017: A browser the daemon runs, streamed to every viewer

- **Status:** Accepted. Merged to main on 2026-11-10; the decisions marked "to review" are still the product owner's to revisit.
- **Date:** 2026-11-10

## Context

- The desktop app's browser panel is a native web view inside the app (WKWebView, `loft-browser`). The web client ([ADR-0016](0016-web-client.md)) has no such thing to embed: it is a page itself, and the pages a user wants to look at (a dev server on the daemon's machine, a site behind that machine's logins) are not reachable from wherever the browser tab runs.
- One answer to the same problem is a "server browser": a real Chromium on the machine that runs the agents, shown to web viewers as a stream of pictures and driven by sending their input back.

## Decision

**The daemon runs its own browser and streams its pages.** Every Browser tab is a view of one of those pages: the web client's, the desktop app's (since 2026-11-15, §6) and a window on another computer's. Agents drive the same pages (§5).

### 1. The browser

- A Chromium-family browser that is already installed (Chrome, Chromium, Edge or Brave; `[browser] executable` picks one). Agentloft doesn't ship one.
- Headless, with a profile of its own under the Agentloft home (`browser/profile`, mode 0700), so its cookies and logins are separate from the user's everyday browser.
- Driven over the DevTools protocol on a **pipe** (`--remote-debugging-pipe`), not a port. Only the daemon holds the pipe; no other program on the machine, and no web page, can attach to it.
- Started with the first page, asked to close when the daemon stops, and stopped five minutes after its last page closes.
- Settings ▸ Browser (`[browser]` in `config.toml`) holds what both browser panels share, the search engine and the home page, and which browser the daemon runs. A browser session may change the first two, not the last.
- Downloads are refused. A window a page opens becomes another tab of the thread (§9; until 2026-11-16 it loaded in the page that opened it). A script dialog is answered for the page (yes to notices and to leaving, no to questions) until dialogs are shown to the viewer, except on a page an agent is driving, where it is held for the agent a while (§7).

### 2. Pages and pictures

- One page per thread (`PageOpen`), kept the size of the view that shows it.
- While someone watches (`Topic::Page`), Chrome's screencast sends JPEG pictures. The daemon keeps only the newest and announces it; each viewer acknowledges what it has shown (`PageFrameAck`), and is sent the newest while it has fewer than its window on the way. **The window follows the link** (`PictureWindow` in `loftd/src/conn.rs`): it grows while acknowledgements come back as fast as the quickest seen, and shrinks once they are slower by more than about one picture's worth, which means they are waiting in a queue. One at a time (as first built) a far link got one picture per round trip: on a phone through the tunnel at 500 ms, about two a second; with the window, about seven, no staler. A slow link still gets fewer pictures instead of a growing queue. Nobody watching, no pictures.
- Chrome is acknowledged no sooner than 70 ms after a picture, which caps the stream at about 14 a second.
- Screencast pictures are one device pixel per CSS pixel. When a page holds still for 250 ms, one screenshot at the viewer's real scale replaces them, so text is sharp on a high-density screen without paying for it while scrolling.
- **While the app on the daemon's computer watches** (§6), nothing between it and Chrome is slower than memory, so the page is pictured for it instead: every device pixel, at up to 60 pictures a second (acknowledged after 16 ms). Nothing blurred turns sharp, and video and scrolling move as in a browser of its own. A headless screencast is drawn at the browser's own density, not the page's (`Emulation.setDeviceMetricsOverride` changes what a page lays out and is screenshotted at, not that), so the browser is started at a dense screen's (`--force-device-scale-factor=2`) and the pictures for viewers elsewhere are made smaller from it. Viewers elsewhere get the big pictures too while the app watches, as many as their link carries.
- **Pages see an ordinary browser.** A browser driven over the DevTools pipe tells pages so (`navigator.webdriver`), and sites act on it: YouTube stops a video after about 40 seconds with "Something went wrong", and Google sign-in answers "This browser or app may not be secure". A person uses these pages, so the browser is started with `--disable-blink-features=AutomationControlled`, as its user agent already drops "HeadlessChrome".
- **Passkeys are declined at once.** Chrome asks for a passkey in a window of its own, which a headless browser never shows, so a site asking for one waited for ever (Google: "Verifying it's you… Complete sign-in using your passkey"). Each tab has a DevTools virtual authenticator that declines everything (`isUserConsenting: false`): a request fails within milliseconds, as when a person cancels, and the site offers another way in. Nothing can be made on it, so no site keeps a passkey that would be gone when the browser stops. The user's own passkeys (in their keychain or on their phone) can't be reached from this browser.
- Pictures travel as base64 inside the same JSON messages as everything else.

### 3. Input

- The viewer sends what it did (`PageInput`): mouse, wheel, keys as a DOM `key` and `code`, and text. The daemon replays it into the page as real input events (`Input.dispatch…`), in the order it was sent: one task per page, fed from the connection's ordered path, as terminal keystrokes are.
- Chrome answers a wheel turn or a pointer move once the page has handled it, about a display frame later, and a trackpad sends more than that. What queued up meanwhile is merged before it is replayed: wheel turns into one by their sum, pointer moves into the last. Replayed one by one, a page kept scrolling for most of a second after the fingers stopped.
- The viewer's pointer is over a picture, so it is told what the page wants under it (`PageInfo.cursor`): after a pointer move or wheel turn the daemon asks the page what its CSS says at that point, or for `auto` what a browser would show (a hand on a link, an I-beam on text and in fields). Asked beside the input, never holding it up, and only for the latest point.
- A typed character goes as its key press, so pages that listen for keys work. A paste or an input method's text goes as text.
- Copy and cut read the page's selection and put it on the **viewer's** clipboard. The page's own clipboard is the daemon machine's and is left alone.
- On a Mac, the editing commands that the system's key bindings would have produced (⌘A, ⌘Z, ⌥←, …) are named explicitly, because a headless page gets none of them otherwise.

### 4. Who may use it

- Local clients: always.
- A browser session: `[web] allow_browser`, with the same rule as terminals. Unset, it is allowed while only this machine can reach the listener (a loopback address and no `allowed_hosts`) and refused once another address, a proxy or a tunnel is involved. Settings ▸ Web access has the switch. The session learns which in its `Welcome`.
- A page may be sent to `http`, `https` and `about:blank` addresses only: not to the browser's own pages, and not to local files, except by an agent (`navigate`, for HTML it built) or a client on this computer (`PageOpen`/`PageNavigate` over the Unix socket). Never by a browser session.
- A page that has shown a local file may go back to it, but any other local document it asks for (for itself or a frame) is refused before it loads (`Fetch` holds the page's `file:` documents once it has shown one). Web pages can't open local files at all; Chrome sees to that.

### 5. Agents (added 2026-11-15)

- **There is one browser.** An agent's `browser_*` tools (`BrowserCall`) run on the thread's page of the daemon's browser, over the same DevTools connection, so the agent, the app and the web client see and drive one page. A thread without a page gets one (1280×800 at scale 2) until a viewer gives it its own size.
- The commands, their results, errors and timeouts are the ones the app's WKWebView panel had (`loft-page-script`, shared with `loft-browser`). Helpers run in an isolated world of the page; `eval` in the page's own. A click is real input (`isTrusted`) at the element's centre when that is where the element is, else the helper's synthetic click. A screenshot is a PNG of the viewport at the page's scale.
- Commands for one page run one at a time. Every client subscribed to the thread is told an agent is using its page (`ServerMsg::PageDriven`, at most once a second per page), so a window can show it; a browser session only if it may use the browser.
- The app no longer hosts agents' browser: the `ClientCall` / `ClientCallResult` messages and the `"browser"` capability are gone.

### 6. The desktop app (added 2026-11-15)

- **The desktop Browser tab is the thread's streamed page too**, so the app, the web client and the thread's agent show one tab: what is open in the app is what the web shows. The native WKWebView panel is gone (`loft-browser` keeps only the native host of agents' views, ADR-0018, and menus).
- **Several tabs per thread** (as in T3 Code). They are the daemon's, so every window has the same ones: opening or closing one is told to everyone who has the thread open (`ServerMsg::PageTabs`, all of them, oldest first), and a window asks for them when it first shows the thread (`PageList`), so they come back after the app restarts. `PageOpen` joins a named tab, opens another (`new_tab`), or joins the one the thread used last. That last one (a person's press or key, or the agent's own) is the one the agent drives.
- **Viewers of different sizes.** The page has one viewport. A viewer that opens or uses it (a press, a key) gives it its own size; the others draw it scaled down to fit, centred, and map their input through that scale. Closing a viewer doesn't close the tab; closing the tab does, and a tab nobody watched or used for an hour is closed by the daemon.
- **What the native panel's toolbar had, on the daemon's page** (`pages/tools.rs`): a screenshot for the composer (`PageCapture`), notes for the agent (`PageAnnotate`/`PageUnpin`: `annotate.js` in an isolated world, notes sent to whoever touched the page last as `PageAction::Note`), zoom (`PageZoom`: fewer, bigger CSS pixels in the same room), hard reload, clearing cookies and site data or the cache (`PageClearData`).
- **Responsive mode** (as in T3 Code; `PageEmulate`): the page gets a size of its own, a phone's or a tablet's (mobile metrics, touch, user agent) or any width × height. A strip under the toolbar picks the screen, takes the size, locks the proportions and rotates; handles on the page's sides and corners resize it by dragging. Every viewer shows the page at that size.
- **A magnified page** (a phone's page that lays out wider than the phone) is pointed at in the page's own pixels: input is divided by the `pageScaleFactor` Chrome reports with each picture, as DevTools does.
- **A project action's preview** (`PageNav::Preview`) is asked for again while its server isn't listening yet, for up to 45 s or until the tab goes elsewhere.
- Pages present an ordinary Chrome's user agent (a headless one names itself so, and some sites turn it away).
- **Sound plays on the daemon's computer only, and only for someone there** (`pages/sound.rs`). A tab is muted unless an app on that computer watches it (the app's hello says `sound`; a browser session's or an SSH window's never counts) and nobody elsewhere used it since: a tap from a phone mutes it again, a press in the app, or the pointer passing over the page there, unmutes it. A pointer passing over the page elsewhere uses nothing (on the same Mac, the mouse crosses a web client's window on its way back to the app). The DevTools protocol can mute only the whole browser (`--mute-audio`), so Chrome's own tab muting is reached through a small extension of ours (`pages/sound/`), loaded over the pipe (`Extensions.loadUnpacked`, which needs `--enable-unsafe-extension-debugging`). It mutes every new tab and unmutes the ones the daemon names. A browser that won't load it is started muted whole. The web client and SSH windows get no sound.
- **Lost with the native panel:** the Web Inspector. Logins made in the native panel don't carry over; the daemon's browser has its own profile.

### 7. Agents' page tools (added 2026-11-16)

Tools for agents on a page, over the same DevTools connection; the set of tools was inspired by OpenCode Browse 0.1.0 (MIT, Anomaly) (`pages/interact.rs`, `input.rs`, `human.rs`, `dialogs.rs`, `frames.rs`, `challenge.rs`, `uploads.rs`; the commands in `loft-page-script`). The wire shape of the earlier commands is kept: what was added is optional.

- **Targets.** Every element tool takes a snapshot ref (`[ref=N]`, as before) or a selector: CSS through open shadow roots, or `text=`, `label=`, `placeholder=`, `role=button[name="…"]`, `testid=`, chained with `>>`, `>> frame >>` into a frame of the page's own site, `>> nth=N`. A selector must match one element (or one visible one); several are named back. Pointer tools also take a point (x, y).
- **Real input, trusted.** Clicks (any button, double, with keys held), hover, drag and the wheel are `Input.dispatchMouseEvent`; `type` and `press` are `Input.dispatchKeyEvent` key by key (US layout, `key`/`code`/text, modifiers, the Mac editing commands of §3) and `Input.insertText` for what no key types; `fill` puts a field's value in with one `Input.insertText` over its selected content. Only what real input can't reach (an element under another, or in another site's frame) gets a dispatched click, and the result says so. HTML5 drag and drop is finished here (`Input.setInterceptDrags`, `dispatchDragEvent`), since a headless browser can't.
- **Human-like input** (`[browser] human_input`, on by default; Settings ▸ Browser): curved, eased pointer paths from where the pointer was, presses off-centre and held a little, keys 30–110 ms apart, wheel scrolls gliding in frames. Bounded so tools stay quick: a move takes at most 0.7 s, typing at most about 3 s whatever its length, `fill` is never paced.
- **Dialogs.** On a page an agent is driving (a command running, or one ended less than 30 s ago) an `alert`, `confirm` or `prompt` is held open instead of answered (§1): the command that opened it stops waiting and returns `dialog: {type, message, default}`, other commands fail saying so, and the agent answers with `dialog`. Nothing gets stuck on it: unanswered for 30 s, or once a person presses or types on the page, it is answered as before (yes to notices, no to questions), and the agent's next result says so (`dialog_answered`). `beforeunload` is always answered at once.
- **Waiting** (`wait_for`): text appears or goes, an element reaches a state, the address matches (a part, a glob, `/regex/`); 10 s unless told, 60 s at most, failing with what it still waited for.
- **Uploads** (`DOM.setFileInputFiles`): only regular files under the thread's workspace or the temporary folder, after following links, and not hard-linked from elsewhere.
- **WebMCP** (`navigator.modelContext`): the page's tools listed and called, read in the helpers' world, or in the page's own when a script of the page's provides them (a polyfill); what they say is labelled as the website's.
- **The outline.** Values typed into fields are never shown (a field says `filled`; a read-only field that holds no secret shows its value; `fill` shows a password's or one-time code's length only). When the page has exactly one main area holding most of its text, and no modal is open, the outline is scoped to it, plus the header's search and buttons, and a note says how much was left out (`within: "page"` for everything, or a selector for one part). Frames of the page's own site are read from the top document. Another site's frame is read over its own session: attached to (`Target.setAutoAttach`, iframes only, the first time an agent reads the page) when it is out of process, through the page's session when not; its `<iframe>` is matched with `DOM.getFrameOwner`, and its refs count from its number × 100 000, so actions on them run in that frame and real input is moved by where the frame is. At most 8 such frames, one level down.
- **Bot checks.** After a load (navigate, back, forward, reload, an action that navigated) the page is classified (`challenge.rs`, from what `loftProbe` reads in the page: Cloudflare, PerimeterX, DataDome, Akamai, Imperva, AWS WAF, captcha walls, "access denied"); a check that clears by itself is waited for up to 10 s. Otherwise the result carries `challenge` and advice: hand the page to the user (`browser_handoff`) or stop, never solve it or retry in a loop.
- **Nothing in the page.** No `Runtime.enable` or `Console.enable`. The helpers run in an isolated world, refs live there (a `WeakMap`, so no `data-*` attributes and no mutations a page could see, as the earlier helpers left), and only `eval` and a page's own WebMCP script run in the page's world, inside a function that leaves no globals.
### 10. Scripts (added 2026-11-16)

- **`browser_execute {script, tab?, timeout_ms?}`: JavaScript that drives a thread's tab in one call**, inspired by OpenCode Browse's `execute` and written for Agentloft from a behaviour spec (none of Browse's code). An agent that would otherwise call snapshot, click, type, snapshot again… one tool call at a time sends one script: inspect, act, verify. Every agent gets it beside the plain `browser_*` tools (Browse gives clients other than OpenCode only `execute`; we keep both, the plain tools being what most agents already know).
- **It runs in the daemon** (`loft-page-exec`, used by `loft-core`'s `scripts.rs`), in an embedded QuickJS (`rquickjs`, MIT), one runtime on a thread of its own per run. Limits: 2 s of JavaScript without an `await` (a loop that never yields is stopped), a 64 MB heap, a 1 MB stack, 60 s overall by default (`timeout_ms`, at most 10 minutes, paused while a handoff waits on the user), eight scripts at a time in the daemon and one at a time per tab. The engine reaches nothing but the browser commands and its timers: no network (`fetch` belongs to the page, through `page.evaluate`), no processes, and **no files**. Browse lets a script read and write inside "file roots"; here a script runs as the daemon, outside the agent's own sandbox and permission prompts, so writing into the workspace from it would get round them. A script returns its data and the agent writes it with its own tools.
- **Every step is a `BrowserCommand`**, the same ones the plain tools send, on the same page and under the same rules (§4, §5): `browse.<command>(args)` is turned into `{"action": "<command>", …args}` without a table (camelCase names and keys become snake_case, `ref` is `ref_id`), so commands added later are scripts' at once, and one this Agentloft doesn't have fails saying so. On top is a Playwright-style layer of our own (`page.goto`, `locator`, `getByRole`/`getByText`/`getByLabel`…, `fill`, `click`, `press`, `waitForURL`, `evaluate`, `screenshot`, …), plus `snapshot()`, `ref(N)`, `handoff()`, `console`, timers and `state`. Calls the commands can't do throw an error that names what to use instead.
- **Locators become refs.** Browse runs Playwright's injected selector engine in the page. We don't ship it: a locator is a chain of steps (CSS, text, role and accessible name, label, placeholder, alt, title, test id, `nth`, `has_text`, `visible`) that a new command, `Locate`, resolves in the helpers' isolated world (`loftLocate` in `agent.js`), giving the matches refs as the snapshot does. Clicking, typing and the rest then go through the ref commands, so a script's click is the same real click (§5) as `browser_click`. Locators are strict (an action on a locator that matches several elements fails) and wait up to 10 s for their element. Reading an element (`textContent`, `inputValue`, `evaluate`) is the `EvalOn` command: the function runs in the page's own world on the elements the refs stand for, and the page never sees the refs.
- **`state`** is an object kept with the tab between runs (in the daemon's memory, as JSON, up to 1 MB), so a script can pick up where the last one left off.
- **The result** starts with `tab: <id>` (the tab `page` ended on, to pass back as `tab`), then the returned value as JSON (up to 100 000 characters) or the error with the script's line, warnings, where the page went ("moved from … to …; 2 navigations"), and the console (200 lines). Pictures the script returns (`return await page.screenshot()`) come back as MCP images, at most 8 and 24 MB; ones taken and not returned are only counted, to save the agent's context. A script that throws or runs out of time is a result with `isError`, not a failed request.
- **The sandbox protects the daemon's machine from a script, not a page from the agent**: the agent could run any JavaScript in the page with `browser_eval` anyway.
- **How a run is built.** The engine thread runs the script's jobs until none is left, then blocks on the daemon's side for whatever settles next (a command's answer, a timer); it never waits on anything itself, so the daemon's clock alone ends a run that takes too long, and dropping the request stops the engine. Up to 32 pictures a run are kept outside the script's heap; the script holds a small image object that renders as `{type: "image", …}` and attaches the picture only if returned.

### 8. Agents' capture tools (added 2026-11-16)

Inspired by OpenCode Browse's capture tools, which fit an agent that watches a page closely (`pages/capture/`). The code is our own, written from a description of each tool's behaviour. They are `BrowserCommand`s like the others, run on the thread's page, one command at a time.


- **`screenshot` takes options; with none it is what it was** (the viewport, a PNG at the page's device scale). It may take the whole page, an element (a snapshot ref, or a CSS selector with ` >> ` into shadow roots; scrolled into view if it fits) or a rectangle, at one image pixel per CSS pixel (`scale: "css"`, where image coordinates are click coordinates), as PNG or JPEG. `labels` numbers the interactive elements in view on the picture, drawn there, never on the page. An image returned is at most 8000 px a side and 3.75 MB (taken again smaller, with a note, if not); one saved, 16384 px. A whole page taller than Chrome can take at once is taken in strips.
- **`screenshot_diff`** compares a fresh screenshot with the tab's last one (taken again with the same region and scale) or one kept by name (`baseline`, eight a tab, in memory): how many pixels changed, where (boxes in CSS pixels), and the diff image (pixelmatch's colour distance and look, written here).
- **`network_*`** captures the tab's traffic over the `Network` domain, which is on only while a capture runs (or emulated network conditions need it), so pages are not slowed otherwise. It sits beside the `Fetch` interception local files use (§4); the two don't see each other's requests. Stop returns every exchange (1000 at most), JSON, form and multipart bodies as text (1 MB each, 25 MB a capture), others only described, **credentials always redacted** by name and by shape (`capture/redaction.rs`, rules after Browse's, a few tightened): authorization and API-key headers, cookie values, secret-named fields, token-like path segments, a password in an address, and any captured secret wherever it shows up again (a credential first seen in a later exchange is taken out of earlier ones too). Addresses and form bodies keep every byte that isn't redacted. A name's `auth` doesn't count inside `author`, nor `otp` inside a word (`footprint`), nor `code` after a kind that is never a credential (`status_code`); `passphrase`, `jwt`, `pin`, `private_key` and a bare `key` do count. Booleans are never chased elsewhere, a number only from six digits, and a one-time value (a password, a code) only from four characters. An answer over 1 MB is saved to a file and returned in brief.
- **`console_*`** keeps the page's console messages, uncaught errors and the browser's own errors. It needs `Runtime`, which a page can detect, so it is on only between `console_start` and `console_stop`, and nothing else turns it on. Messages from isolated worlds (our helpers') are left out; what `Runtime.enable` replays from before the start is told apart by its timestamp. 1000 kept.
- **Both follow the page's frames of other sites** (`pages/capture/cross_site.rs`). Under site isolation such a frame is a renderer and a DevTools target of its own, whose requests and console the page's session never sees (and where its own document's response ends). While a network or console capture runs, the page auto-attaches to them (`Target.setAutoAttach`, iframes only, as for agents' reads in §7; popups come from `Target.targetCreated`, §9) with `waitForDebuggerOnStart`: a frame made meanwhile waits until the capture's domains are on in it, then is let run (`Runtime.runIfWaitingForDebugger`, sent whatever else happened), so its first request and message are captured. Frames already there when a capture starts are followed from a moment after. Each frame's session gets the same domains as the page (`Runtime` and `Log` only while a console capture runs) and loses them when the capture ends; then new frames no longer wait (auto-attach itself stays on). The daemon's event loop gives the frames' events to the page's captures, so they are in time order with the page's own; an exchange or a message a frame's session saw says so (`frame`: its origin, never its path), and a frame's bodies are asked for over its session. A frame's own frames of other sites are followed the same way. Workers are not followed, and frames' `file:` guarding (§4) is not part of this.
- **`recording_*`** records the tab: **a recording is one more watcher** of the page's screencast (§2). A page nobody watches is pictured for it; viewers' pictures are the same with or without it. Frames are written as MJPEG into Matroska as they come, by a thread of its own (our own writer, after the Matroska specification); `.mp4` and `.webm` are made with ffmpeg when it stops, if installed. The screencast is the viewers' size (CSS pixels, or every device pixel while the app here watches), so a file takes its first frame's size and scales other frames to it. It stops by itself after its longest or when the tab closes.
- **`emulate`**: a size is the viewers' **responsive mode** (§6), so every viewer shows the page as the agent set it and a person can end it from the strip. Colour scheme and other media features, print media, user agent, geolocation, time zone, locale, network conditions (offline, presets or custom), CPU throttling and touch are the page's alone. Our browser is driven over its own pipe, so time zone, locale and throttling can be set (Browse, through an extension, can't). Geolocation is granted to the site open at the time, for the emulated location only: nobody can answer the browser's question in a headless browser. `reset: true` puts back everything the agent set.
- **Files** (recordings, saved screenshots, saved captures) go to a folder of the thread's in the temporary directory, the user's only (0700, files 0600). The daemon writes nowhere an agent names: an agent whose own tools may not write somewhere can't get the daemon to write there; it copies a file on itself.
- The MCP tools are `browser_screenshot` (with the options), `browser_screenshot_diff`, `browser_network`, `browser_console`, `browser_recording` and `browser_emulate`; an image comes back as an MCP image, with what was said about it as text.
- Live tests: `cargo test -p loft-core pages::capture -- --ignored`, and the bridge's in `cargo test -p loftd --test workbench live -- --ignored`.

### 9. Agents' tabs and handing over (added 2026-11-16)

Inspired by OpenCode Browse, whose agents keep tabs of their own and hand a tab to a person when only a person can go on. Where ours differs is said below.

- **Tabs are the handle.** Every `browser_*` tool takes a `tab`: the tab's id, or a name the agent gave it (`BrowserCall.tab`). Without one it is today's rule: the tab the thread used last, a new one if it has none. Running a command on a tab makes it the one used last. Results say which tab they ran in (an MCP text block after the result). One entry point runs every command for an agent, whatever asks: `Core::browser_call(thread, tab, BrowserCommand) -> BrowserReply` (`loft-core/src/browser.rs`).
- **`browser_tabs`** lists the thread's tabs (handle, url, title, who opened it, idle time, whether a call runs in it, its limits, whether it waits for the person), opens one (`new`, at `url` or blank, optionally named: asking for a name that is open answers with that tab and doesn't move it), and closes one or all the agent opened. A tab knows who opened it (`PageInfo.agent.opened`).
- **Options fixed at open**: `allowed_origins` (`example.com`, `*.example.com`, `http://localhost:3000`; a private or loopback address only when named exactly; a name only a wildcard matched is looked up, and refused if it resolves to a private address) and `read_only`. They are agents' limits, not the person's:
  - An agent's `navigate` outside the origins is refused before it goes. A document that commits there *while an agent's command runs on the tab* (a click that led there, a redirect) is stopped and the tab sent to a blank page; a popup that does so is closed. The agent is told either way, with its next result.
  - A person may take a tab anywhere (the address bar, during a handoff). Until it is back inside its origins, the agent's commands other than navigate, back and forward are refused there.
  - Read-only refuses everything but snapshot, screenshot, scroll and `eval` after the tab opens. `eval` runs in the page and can change it: read-only keeps an agent from wandering, it doesn't fence it in. (A command added later is refused on a read-only tab until `BrowserCommand::allowed_read_only` lists it.)
  - Requests a page makes itself (fetch, images, frames) aren't filtered.
- **Popups become tabs.** A window a tab's page opens (`window.open`, `target=_blank`) is attached (`Target.attachToTarget`) and set up like any tab (user agent first, then the passkey authenticator, size and focus), with the opener's limits and thread. It doesn't become the tab used last. The agent hears of it as `new_tabs` in the result of the command that opened it (or the next one). It keeps its opener, so sign-in popups that report back to their opener work. One that goes to an address tabs may not be sent to (§4: anything but `http`, `https`, `about:blank`) is closed. Its first page may start loading before its user agent is set (it is attached after Chrome made it): a known gap.
- **Handing over (`browser_handoff`).** For a sign-in, 2FA, a captcha, a payment: the tab gets a card in every window that shows it (site origin, the agent's reason, **Continue**), drawn by the app above the page, so the page can't press it (`Request::PageHandoffDone`, allowed to whoever may use the browser). The thread is `WaitingApproval` with `Thread.handover` set meanwhile, so the Dock badge, the notification ("… needs you in the browser") and the sidebar ("In the browser") work as for an approval. A window that has the thread open brings its panel up on that tab once per handoff; an agent's other tabs never switch what a window shows (they appear beside the person's tab; `PageDriven` no longer switches away from a tab the person opened). The call returns when the person presses Continue (`continued`), the tab closes, the agent's turn ends (`stopped`), after an hour nobody came (`expired`), or when its own wait runs out (`waiting`, default 600 s): then the card stays, and calling again keeps waiting, or answers how it ended if the person pressed Continue in between. While the card is up the agent's other commands on that tab are refused, and the person uses the page as ever.
- **`browser_demonstrate`** is a handoff whose card says "Recording your steps…" and **Done**. The steps come from the person's own input (`PageInput`, whichever window it comes from): a press is described by the element under it (role, accessible name, CSS path), typing by the focused field, with nothing of a password or one-time-code field kept but its length, other keys by name; navigations come from the page's events. Nothing is installed in the page to watch it: what is recorded is what people send through a window, which is all the input there is here.
- **`browser_status`**: whether the browser runs, which program it would run or why it can't (and what to tell the person), the thread's tabs and what waits for the person. It never starts the browser.
- **Idle tabs**: a tab nobody watched or used for an hour still closes, but never a named one or one waiting for the person.
- **Guardrails, compared with Browse.** Browse forwards raw DevTools commands, so it filters them (cookies, permissions, closing the browser, storage of other sites). Our agents have no raw DevTools: only the commands in `loft-page-script`, so there is nothing of that kind to filter. Browser-internal pages, other extensions and DevTools can't be opened (only `http`, `https`, `about:blank`, and local files the daemon itself loaded, §4); a renderer can't navigate to them either, and a popup that tries is closed. The real difference is ownership: in Browse an agent uses only tabs it opened or the user lent it. Here the thread's tabs are one set shared with the person, so a tab the person opened stays usable by the agent; the tool descriptions ask agents to open their own and to use the person's only when asked, and `opened_by` in the list says whose is whose.
- **What stops a determined agent:** nothing new. The agent runs as the user and can reach the daemon's socket, so it could send `PageHandoffDone` itself, as it could answer its own approvals. The card guards against pages, not against the agent.
- The MCP bridge answers tool calls as they finish rather than in order, so one waiting for a person (or for other threads) doesn't hold up the others.

## Why not something else

- **Stream the desktop app's WKWebView.** It has no screencast and no way to inject trusted input; it would only work while the desktop app runs, and badly.
- **Proxy the page into an `<iframe>`.** Works only for sites that tolerate being framed and rewritten, puts another origin's script next to ours, and gives an agent nothing to drive.
- **Bundle a browser.** About 150 MB for something most machines already have.
- **A debugging port.** Any local program, including one run by another user of the machine, could attach to a browser that holds the user's logins.

## Consequences

- The web client's browser needs Chrome (or a sibling) on the daemon's machine. Without one the tab says so.
- Agents drive the daemon's browser (§5): they have one whether or not a window is open, and it needs Chrome (or a sibling) on the daemon's machine like the web client's. Without one, their browser tools say so.
- A page an agent opened keeps running in the daemon's browser after the window that showed it is closed, until the thread's tab is closed or the browser stops.
- A browser on the daemon's machine reaches what that machine reaches (its localhost, its network) and keeps logins. That is the point, and it is why a session reachable from elsewhere doesn't get it unless asked for.
- A picture is a picture: no text selection drawn by the viewer's system, no native menus, no screen readers inside the page.

## What's left

- One controller at a time: today an agent's commands and a person's input can interleave on the same page.
- Dialogs shown to the viewer (today a person's press answers one held for the agent as nobody's would be), file choosers and downloads; tools for agents to open and pick tabs themselves; the pointer's shape; an input method's text shown while it is being composed.
- Agents' page tools (§7): selectors don't reach into another site's frame (refs and points do); frames of other sites inside such a frame aren't read; no upload into another site's frame; `wait_for` has no network-quiet condition.
- A popup's first request may still carry the headless user agent (§9): pausing new windows until they are set up (`Target.setAutoAttach` with `waitForDebuggerOnStart`) would close it.
- Demonstrations see what a window sends: a click inside a cross-origin frame is described as the frame, and a person's steps in a popup the demonstrated tab opened aren't recorded.
- Agents' tabs end with the browser (and the daemon): unlike Browse, names and options aren't kept across a restart.
- Smaller, moving pictures on a slow link (half scale while scrolling), and binary frames instead of base64.

## Decisions to review

1. **A daemon-owned Chrome for the web client, the native view staying in the desktop app.** The alternative is one browser for both, with the desktop panel becoming a stream too. *Decided 2026-11-15: one browser, the daemon's,* for agents (§5) and the desktop tab (§6).
2. **Using the installed browser** rather than shipping one.
3. **On for a local-only listener**, off until asked for once other machines can reach it (as for terminals).
4. **Its own profile**: nothing is shared with the user's everyday browser, so sites need signing in to once more there.
