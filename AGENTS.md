# Notes for coding agents

Read [CONTRIBUTING.md](CONTRIBUTING.md) first: commands, build speed, architecture rules. This file covers what an agent working in this repo needs on top of that. Whatever agent you are (Claude Code, Codex, OpenCode, …): when you learn something here that the next agent would need, add it to this file, not to your own private memory.

## Before you say a change is done

- `cargo fmt`
- `cargo clippy --workspace --all-targets --features loft-terminal/test-support -- -D warnings`
- `cargo test --workspace --features loft-terminal/test-support`
- Browser-only code (`cfg(target_arch = "wasm32")`) is invisible to native clippy: `RUSTC_BOOTSTRAP=wasm_thread CLIPPY_CONF_DIR=.config/clippy-wasm cargo clippy -p loft-web --target wasm32-unknown-unknown -- -D warnings`. That config forbids `std::time::{Instant, SystemTime}::now`: they panic in the browser, which freezes the whole web client. Use `web_time`.
- After touching dependencies or their features: `cargo hakari generate`.

Run the full suite once, in the background if your tool allows it, saving the output to a file you can grep. Don't run it twice.

## The web client is the same UI, built separately

- The browser version is `loft-ui` compiled to wasm, served by the daemon from the app bundle's `Resources/web` (copied from `target/web`). `cargo xtask dev`, `bundle` and `install` build it too; only `--no-web` skips it. A web client that "doesn't have" a desktop fix is almost always a stale `target/web`: check its timestamp before debugging the code.
- Clipboard in the browser: `read_from_clipboard()` is always `None`. gpui-kit binds `cmd-v` to `Paste` only for `target_os = "macos"`, so in a browser on a Mac ⌘V is the browser's own `paste` event, delivered to the focused input handler's `paste` (images included, no permission needed). It binds `ctrl-v` to `Paste` in every other build, wasm included; a key GPUI handles gets `preventDefault` from its web platform, so no `paste` event follows. In the browser `browser_paste::key_bindings` binds `ctrl-v` to `NoAction` in the `Input` context, so Ctrl+V is the browser's paste too. Only a context menu's Paste still runs the `Paste` action, which can only read through `read_from_clipboard_async` (permission-gated; the website's frame doesn't grant `clipboard-read`, so there it pastes nothing). The composer handles both: `browser_paste.rs` wraps its input handler, `paste_in_composer` does the async read. The terminal leaves Ctrl+Shift+V to the browser (Ctrl+V is ^V there). Headless Chrome: a CDP key event with `commands: ["paste"]` makes a real paste event; a window `keydown` listener reading `defaultPrevented` shows whether GPUI took the key.
- What differs on purpose is behind `host::IS_WEB` and `store.is_elsewhere()` (ADR-0016's table): Finder, editors, file dialogs, in-place video.

## Dev and stable never share data

- The installed app (`cargo xtask install`, green icon) uses `~/.agentloft`. Dev bundles (`cargo xtask bundle`, blue icon) and debug builds use `~/.agentloft-dev`. An explicit `AGENTLOFT_HOME` overrides either.
- Test instances run on their **own fresh home** (e.g. under `/private/tmp`; `~/Desktop` is TCC-protected), seeded with made-up data. **Never copy the real `agentloft.db` into a scratch home.** A copy holds the user's threads and the pids of their live agents. A daemon's startup reaper (`crates/loftd/src/reaper.rs`) ends recorded agent processes it believes orphaned. It now skips any whose parent is a live `agentloftd`, but treat that as a safety net, not permission.
- Seeding: the `fake` harness (echoes the prompt as Markdown; `approve` opens an approval, `slow` streams slowly, `bgagents` leaves background subagents running, `fail` fails the turn, `limit:<seconds>` fails it as a used-up plan that resets that many seconds from now, `suggest:<text>` offers `<text>` as the next message in the composer, `ui:all` / `ui:<sample>` show agent views) costs no tokens. Create threads over the daemon socket (`<home>/run/agentloftd.sock`; each frame is a big-endian `u32` length then JSON: first `{"type":"hello","protocol_version":1,"client_kind":"local-ui","client_build":"probe"}`, then `{"type":"request","id":1,"body":{"op":"create_thread",…}}`; a subscription's topic is `{"kind":"thread","id":…}`), or insert rows into the scratch `agentloft.db` while its daemon is stopped (backdate `updated_at_ms` by a day for the sidebar's "Older" group; `"status":"archived"` for "Archived").
- Fake CLIs (`gh`, …) for a scratch daemon: it reads its PATH from `$SHELL -l -i -c 'env -0'`, so launch it with `SHELL=<a script that prints env -0 with a stand-in bin dir first>`. In `loft-core` tests, `CoreOptions.env` sets PATH directly.
- To exclude the real `gh` in tests, use an isolated bin directory with the required tools linked in. Don't remove every PATH directory containing `gh`: Ubuntu installs `git`, `cat` and `gh` together in `/usr/bin`.
- A rebuilt app asks the running daemon to make way once, at launch (`Shutdown { reason: Upgrade }`, `crates/loft-client/src/native.rs`). The daemon refuses while a turn is running and does not count background work a thread is waiting on. So relaunching can leave an old daemon in place, or end other threads' background agents and shells. Check before swapping the user's app.

## Seeing a UI change without input access

- Launch: `AGENTLOFT_HOME=<scratch> target/debug/agentloft` (build with `cargo build -p loft-app -p loftd`). It opens the most recently active thread.
- `AGENTLOFT_DEV_TAB=<hook>` drives the first window: panels (`changes`, `terminal`, `browser`, `file:<path>`, `settings:<section>`, …), clicks (`click:x,y,after_ms;x,y,after_ms`, window points; `after_ms` counts from launch), `hover:x,y`, `type:<text>`, `action:<name>` (runs a project action), `palette:<query>`, `do:<steps>` (keys, typing, clicks, double-clicks, right-clicks and drags in order: `dev_script` in `crates/loft-ui/src/workspace/compose.rs`), `all:<hook>++<hook>` (several hooks in one launch), and more. The full list is `apply_dev_tab` in `crates/loft-ui/src/workspace.rs`. Add a hook there rather than posting synthetic OS input.
- Screenshot with `screencapture -x -o -l <window id>`, never a screen region (`-R`): that captures whatever of the maintainer's is in front. A menu is a small window of its own with its own id. Pick the test pid's largest on-screen layer-0 window (`CGWindowListCopyWindowInfo`); the app also owns small hidden windows. Delete screenshots afterwards.
- Documents (pptx/PDF/Office) without the app: `cargo build -p loft-ui --example doc_preview --features loft-ui/shots`, then `target/debug/examples/doc_preview <file> --shot out.jpg` (renders its own frame; no screen permission needed). Notes on it: `--annotate --click x,y --drag x1,y1,x2,y2 --hover x,y [--note text]`; in the app, `AGENTLOFT_DEV_TAB='docnote:<file>|x,y;x1,y1,x2,y2;x,y!|<note>'` (`!` leaves the note box open).
- Web client: `cargo xtask web [--release]` → `target/web`, served by the daemon (`[web] enabled = true` and a non-default `port` in the scratch home's `config.toml`; `agentloftd web --home <dir>` prints the pairing link). Drive it with headless Chrome over CDP using a fresh `--user-data-dir` per build, `Network.setCacheDisabled`, and `Page.bringToFront` (background tabs draw no frames).
- A window that isn't changing paints nothing, so also test after 30+ s idle.
- To bring a test window to the front for a screenshot, `osascript -e 'tell application "System Events" to set frontmost of (first process whose unix id is <pid>) to true'` (then hand the front back to the app that had it). `NSRunningApplication.activate` did nothing for an unbundled `target/debug/agentloft`.
- A scratch home's Device panel lists this Mac's real simulators and emulators and may open one: unless the test is about devices, start the scratch daemon and app with `AGENTLOFT_FAKE_DEVICES=1`.
- A test window covered by the maintainer's own windows is occluded: GPUI stops drawing it, and `screencapture -l` keeps returning its last frame. A screenshot that "doesn't update" is not a freeze until the window is known to be visible. Judge by what the store received (log it) or what the daemon answered, not by pixels.

## Windows and Linux

- Building libghostty-vt fetches Zig packages; one of them (`aro`, wanted by `translate_c`) comes by git from `codeberg.org`, which GitHub's Linux and Windows runners sometimes can't resolve (`UnknownHostName`), failing the build. Both workflows `zig fetch` the same commit by git from `github.com/Vexu/arocc` first (same package hash, so Zig never asks codeberg; fetch it by git, not as GitHub's archive: Zig keeps an archive with its top folder, and a build reusing that copy reports a hash mismatch); after a Ghostty bump, check `zig-pkg/translate_c-*/build.zig.zon` for a new aro commit and update that step. CI also keeps the library's finished builds between runs (`GHOSTTY_VT_CACHE_DIR`).
- Releases: `.github/workflows/release.yml` builds `Agentloft-macos-arm64.dmg`, `Agentloft-windows-x64-setup.exe` (+ `.zip`) and `Agentloft-linux-x64.tar.gz`; a `v*` tag publishes them (the website's download buttons link to those exact names under `releases/latest/download/`). Push to the `release-test` branch to build everything without publishing.
- The daemon's socket is a named pipe on Windows (`\\.\pipe\agentloftd-<hash of home>`, `Paths::socket_file`). Connect and listen through `loft_client::local` (`connect`, `Listener`, `detach`), never `tokio::net::Unix*` directly, tests included.
- Platform code the Mac build never compiles: `cargo xtask cross-check windows` / `cargo xtask cross-check linux` run clippy for those targets from a Mac (the function says what each needs: `cargo-xwin` + Homebrew `llvm`, or `zig`). Run them after touching `cfg(unix)`, `libc`, process spawning, PATH handling or anything under `std::os::*`. CI also builds and lints the app and daemon on real Windows and Linux runners.
- `PATH` is split on `loft_config::PATH_SEPARATOR` and binaries found with `loft_config::which` (it tries `PATHEXT` on Windows: `claude.exe`, `codex.cmd`). On Windows there is no login shell: the env is the process's own; terminals run PowerShell, setup scripts `cmd /C`.
- Stand-in CLIs in tests (`gh`, `cloudflared`, `ssh`) are shell scripts, so those tests are `#[cfg(unix)]`.
- Windows open with `appears_transparent: true` (for the traffic lights), which on Windows removes the whole system title bar. Every window with one must draw its own: `.moves_window()` on each top strip and `title_bar::controls(window, p)` at its right end (`crates/loft-ui/src/title_bar.rs`). Both go through Windows' hit test (`WindowControlArea`), so a control inside a strip must claim its press (`.claims_press()`, gpui-kit `Button`), or pressing it starts a window move instead of a click. Linux asks the window manager for its title bar (server-side decorations; GNOME on Wayland doesn't offer them, untested there).
- What is still macOS-only (degrades quietly elsewhere): the startup reaper (`ps`), the editor list in thread details (`.app` bundles), `scutil` names, the embedded WKWebView (`loft-browser`), in-place video, notifications/Dock badge.

## Agentloft on another computer (SSH)

- A window can show another computer's Agentloft: File ▸ Connect to Another Computer… runs `ssh <host> … agentloftd bridge` (`crates/loft-client/src/ssh.rs`, `crates/loftd/src/bridge.rs`). The bridge joins the SSH session to that daemon's Unix socket, so the connection is the same local one as on that machine. Each window has its own store, so a window is either this computer's or one host's (`AppStore::remote`).
- In views, ask `store.is_elsewhere()` (a browser session or an SSH host), not `host::IS_WEB`, before reading the daemon's files from this disk or offering Finder, editors or the video player.
- Try it without a second Mac: the Docker host in `packaging/ssh-test/README.md`, with `AGENTLOFT_SSH` (a stand-in `ssh`) and `AGENTLOFT_DEV_REMOTE=<host>` (open only a window on that host; `AGENTLOFT_DEV_TAB` hooks then drive it).

## The website and the public address (ADR-0019)

- `cloud/` is the website at `agentloft.promptanddone.com`: a Cloudflare Worker with D1. It does Google sign-in, links computers and hands out tickets. Deploy with `cloud/README.md`; its tests are `cd cloud && npm test` (no dependencies). It never carries Agentloft's traffic.
- A computer is public through Cloudflare Tunnel (`[web] tunnel = "<name>"`, `crates/loftd/src/web/cloudflare.rs`): the daemon creates the tunnel and DNS record once, then runs `cloudflared` as its child and restarts it when it stops. Tailscale (tailnet sharing and Funnel) was built first and removed: Funnel's relay carried about 0.8 MB/s, and nothing needed the tailnet (ADR-0019 §1, §4).
- `[web] tunnel = "quick"` is a Cloudflare quick tunnel (no account; random `*.trycloudflare.com` name read from cloudflared's log, ADR-0019 §4a). Linking the computer turns it on (unless a tunnel is set), and the daemon fetches a pinned `cloudflared` if none is installed (`web/cloudflared_install.rs`; the live test is `cargo test -p loftd --lib installs_the_pinned_release -- --ignored`). Tests that link must set `cloudflared_cli` (a fake, or a path that doesn't exist) or they would start the real one or download it. It runs only while the computer is linked to the website, with a `HOME` of its own so no Cloudflare login is used: a real quick tunnel is safe to try live (it touches no account). Its fake is `fake_quick_cloudflared`.
- Test it with a stand-in CLI: `[web] cloudflared_cli = "<script>"`; `fake_cloudflared` in `crates/loftd/tests/web.rs` is one to copy. Never point a test at the user's real `cloudflared`: it changes their Cloudflare account and DNS. Anything that does use a Cloudflare login uses the `cloudflare_cert` the config names, never cloudflared's default `~/.cloudflared/cert.pem`.
- On the public (tunnel's) name only tickets from the website sign in: no pairing, and sessions made by pairing don't count (`is_public` in `http.rs`). To ask whether a `Host` is the tunnel's name, use `host_listed`, never `host_allowed`: `host_allowed` accepts any IP and `localhost`.
- The website shows a public computer in a frame (`/m/<id>`, ADR-0019 §5), so its address stays the website's. On the public address only, the daemon lets the linked website's origin frame it (`frame-ancestors`, `Website::frame_ancestor`). A ticket redeemed with `framed: true` gets a `SameSite=None; Partitioned` cookie, because a `Strict` one is never sent in another site's frame. Keep both of those limited to the public address.
- To try linking without the real site, set `[web] website = "http://127.0.0.1:<port>"` (plain HTTP is allowed only to this computer). `FakeSite` in the same test file answers the link, poll and report calls. Linking a scratch daemon to the real site shows that computer in the user's list: unlink it afterwards (`{"op":"web_unlink"}` over the socket).

## Gotchas

- Agents' `browser_*` tools run on the thread's page of the daemon's headless Chrome (`crates/loft-core/src/pages/automation.rs`, ADR-0017 §5), not in an app window. The commands and helper scripts are `crates/loft-page-script` . Live tests start a real Chrome on a temp profile: `cargo test -p loft-core pages:: -- --ignored` and `cargo test -p loftd --test workbench live -- --ignored`. In DevTools a page's main frame id is its target id, and `Fetch.enable` with a `file:*` pattern does pause `file:` documents (how pages are kept from opening local files they weren't sent to). The page-interaction tools (click/fill/type/press/select/hover/drag/scroll/wait_for/dialog/upload/webmcp, ADR-0017 §7) live in `pages/interact.rs` and its siblings; `live_an_agent_uses_a_page` there covers them all (a cross-site frame is `localhost` inside a `127.0.0.1` page: different sites, so out of process). Never `Runtime.enable` a page or leave anything in its DOM or window: refs live in the helpers' world (`WeakMap`). A DevTools command that may outlast its wait goes through `Agent::send` (its own task): a dropped `cdp.send` future can stop half-way through writing to the browser's pipe. While a JavaScript dialog is open the page answers no `Runtime.evaluate` or `Input.*` (they hang), so nothing on the browser's event loop may await one on a page whose dialog is held (`dialog_held`).
- `browser_execute` scripts run in QuickJS inside the daemon, one runtime on a thread of its own per run (`crates/loft-page-exec`, ADR-0017 §10). `engine.rs` runs the JavaScript under its limits and blocks on the host when it has nothing to run; `host.rs` runs the commands and timers it asks for, keeps the clock, console and pictures, and writes the result; `prelude.js` is the Playwright-style layer. `browse.<name>(args)` becomes a `BrowserCommand` through its serde `action` tag (`mapping.rs`), so a new command needs no change there. Locators resolve through the `Locate` command (`loftLocate` in `agent.js`) into refs; element reads go through `EvalOn`. `loft-core`'s `Tabs` adds `tab` (and `new_tabs`, `notes`) to object results, except what the page's own JavaScript returned (`eval`, `eval_on`, `webmcp`). Engine tests use a fake `Tabs` (`cargo test -p loft-page-exec`); the live one is `cargo test -p loftd --test workbench live_a_script -- --ignored`.
- Agents' typing and pasting (ADR-0017 §7): every key waits for the page's next frame and the task after it (`Input::settle` in `pages/input.rs`), or editors that redraw a frame later lose keys. `paste` (`browser_paste`, a script's `locator.paste`/`keyboard.paste`) writes headless Chrome's own in-memory clipboard from the helpers' world and presses ⌘V with the `paste` editing command: a trusted paste event, and this computer's clipboard is never touched (to check, compare the Mac pasteboard's `changeCount` before and after; don't read the user's clipboard). The page for live tests is `crates/loft-core/src/pages/testdata/editor.html` (redraws like a React editor, pastes like Lexical). To try real editors with no website: `npm install lexical @lexical/rich-text prosemirror-view … draft-js react esbuild` in a scratch folder, bundle each with esbuild and serve it on `127.0.0.1`; drive it with `browser_execute` over a scratch daemon's socket (`browser_call` with `{"action":"execute",…}`).
- A cross-site iframe (out of process) talks over its own DevTools session, attached by the page's `Target.setAutoAttach` (`pages/frames.rs`). `Browser::run` routes those sessions' events only to captures (`capture/cross_site.rs`, by `Captures::frame_page`); anything else that needs a frame's events must be routed there too. Captures attach with `waitForDebuggerOnStart`: without it a new frame's first requests race `Network.enable` on its session (the live test missed them about one run in three). Every frame that arrives waiting must get `Runtime.runIfWaitingForDebugger`, or it stays blank.
- Every Browser tab (desktop, web, SSH window) is the thread's page of the daemon's browser, streamed (`crates/loft-ui/src/panel/page.rs`, ADR-0017 §6): a thread's tabs are the daemon's (`PageTabs`/`PageList`), so every window has the same ones, and the agent drives the one used last. A viewer that isn't the page's size draws it scaled to fit and takes it back on a press or key. To see what the app shows without screen access, ask the daemon: `{"op":"page_capture","id":…}` answers a PNG (pins included). `page_resize`, `page_emulate`, `page_zoom`, `page_annotate` over the socket act like another viewer. A test page without `<meta charset>` shows "×" as "Ã—": that's the page, not the stream. A view whose size isn't known yet asks for the next frame (`request_animation_frame`): a window that nothing else changes draws no more frames, and a tab switched to for the first time would never open. `AGENTLOFT_DEV_TAB=browsertab` opens another tab. On a phone, GPUI's web platform shows the keyboard after a tap only if the tapped view's `accepts_text_input` says yes: the page view says so only for a tap on one of the page's text fields (`PageInfo.fields`, found by the daemon), or the keyboard comes up for every tap. While the app on the daemon's computer watches a tab, the tab is pictured for it at every device pixel and up to 60 a second (`Pictures::Here`); viewers elsewhere get one pixel per CSS pixel at about 14. A headless screencast is drawn at the browser's density whatever the page's emulated one, hence `--force-device-scale-factor=2`. Pages must not see `navigator.webdriver` (`--disable-blink-features=AutomationControlled`): with it, YouTube errors after ~40 s of a video and Google refuses sign-in. A site error that appears "after" some viewer action may just be time: check with a control run that does nothing. Passkey requests are declined at once by a virtual authenticator per tab (a headless browser can't show the passkey window, and pages waited on it for ever). The pointer a page wants is looked up after each move (`follow_pointer`, `CURSOR_SCRIPT` in `pages/tools.rs`) and drawn by the tab's `page-viewport` element (and a view's own). Pictures to a viewer go out several at a time, as many as its link carries (`PictureWindow` in `loftd/src/conn.rs`); to try a far link, put a Unix-socket proxy that delays and rate-limits between a probe and the daemon's socket, and time frames and queue waits. A tab nobody watches draws no frames and runs no timers: live tests that need a page's timers call `watching(.., true)`. A test HTTP server must serve each connection in its own task: Chrome opens spare connections and never uses some, and a server that awaits one blocks the next navigation ("the browser didn't answer `Page.navigate`"). To measure the stream without the app, subscribe over the socket and time the frames: a page that keeps scrolling after the input stopped means input is queuing (wheel and move are merged in `replay_input`). The daemon's Chrome plays sound on its own computer: a tab is unmuted only while an app there watches it (hello capability `sound`) and nobody elsewhere used it since (`pages/sound.rs`, through a small extension, since DevTools can only mute the whole browser). To check it without hearing anything, play a 20 Hz tone at gain 0.0005 and ask CoreAudio whether the default output is running (`kAudioDevicePropertyDeviceIsRunningSomewhere`).
- Agents' capture tools (`crates/loft-core/src/pages/capture/`, ADR-0017 §8: screenshot regions and diffs, network, console, recording, emulate) keep pages undetectable: `Runtime.enable` only between `console_start` and `console_stop`, `Network.enable` only while a capture or emulated network conditions need it (`network_on`/`network_off`). A recording counts as a viewer (`Browser::watching`), so don't stop a page's screencast behind its back. Files they write go to `<temp>/agentloft-browser/<thread>/`, never a path an agent names. Live tests: `cargo test -p loft-core pages::capture -- --ignored`. The browser follows this Mac's light/dark appearance, so a test that checks `prefers-color-scheme` compares with the page's own value first.
- Android emulators (`crates/loft-core/src/devices/android/`, ADR-0020) are driven through the emulator's own gRPC service (`EmulatorController`, messages hand-written in `grpc.rs` over `h2`). The daemon starts them with `-no-window -grpc-use-token` as their own process group (never recorded, so they outlive the daemon and the reaper leaves them); a running one describes itself in a discovery file `pid_<pid>.ini` (port, `grpc.token`; `~/Library/Caches/TemporaryItems/avd/running` on a Mac). One started by Android Studio has no token (it uses signed JWTs): listed and stoppable, but its screen can't be shown. An AVD with `hw.keyboard = no` (avdmanager's default) has no keyboard device, so the emulator's key events go nowhere: keys then go through `adb shell input`. No AVD has a mouse, so a scroll is a short drag of a second finger that holds still before lifting (no fling). The touch screen doesn't turn with the picture: points are mapped by the rotation sensor's turn (`input.rs`). Pictures are JPEG-encoded in the daemon: about 5 ms each in release, 50 ms in a debug build (the encoder is generic, so it's compiled at the caller's opt-level), so a dev daemon streams at a third of the rate. Live test: `cargo test -p loft-core devices::android -- --ignored --nocapture` (boots `Pixel_8_Play`, or `AGENTLOFT_TEST_AVD`; stops it again if it was stopped).
- Android foldables, several fingers and settings (`android/fold.rs`, `android/settings.rs`): try them on AVDs of your own in a scratch AVD folder, never the user's: `ANDROID_AVD_HOME=/private/tmp/<dir> avdmanager create avd -n Test_Fold -k "system-images;android-35;google_apis_playstore;arm64-v8a" -d pixel_9_pro_fold` (`6.7in Foldable` is a flip without a cover screen, `8in Foldable` folds outward); the backend and the emulators it starts take `ANDROID_AVD_HOME` from its env. `cargo test -p loft-core devices::android::tests::live_a_foldable -- --ignored --nocapture` makes, folds, pinches and deletes one by itself. The emulator's `getStatus.booted` comes before adb can reach the device on a cold boot: booted also waits for `sys.boot_completed`. `cmd notification post` lands a moment after it returns. On the cover screen touches are still in the main display's pixels. This image has no Google Maps; a picture opened in Photos (`content://media/...`) is what the live test pinches. `adb exec-out screencap -p` on a foldable prints a warning into the PNG: use the gRPC screenshot.
- Physical Android phones (`crates/loft-core/src/devices/android_phone/`, ADR-0020, `android:@<adb serial>`) use adb alone. Pictures: `screenrecord --output-format=h264` through `adb exec-out`, cut into pictures by `h264.rs` and decoded by VideoToolbox (`videotoolbox.rs`, hand-written FFI, macOS only; ImageIO encodes the JPEG, so a debug daemon is as fast as a release one), else ffmpeg, else `screencap`; `AGENTLOFT_PHONE_DECODER=ffmpeg|screencap` picks a later one first. An Annex B stream doesn't say where a picture ends, so the last one is taken as complete after a quiet moment; the quiet time doubles per phone each time a picture turns out to have come in parts (frequent on an emulator under load) and a new recording takes over from a keyframe. Touches: Android's own `uinput` shell command makes a virtual touch screen (`touch.rs`); `sendevent` to `/dev/input/event*` is refused to the shell by SELinux on `user` builds, emulators included. Keys and text: `input` (ASCII only). No phone needed to try it: a running emulator counts as a phone with `AGENTLOFT_PHONE_INCLUDE_EMULATORS=<serial>[,…]` (or `1` for all) in the daemon's environment. Live test against your own emulator (`emulator -avd <name> -no-window -read-only -port 5600`): `AGENTLOFT_TEST_PHONE=emulator-5600 cargo test -p loft-core devices::android_phone -- --ignored --nocapture` (fps, touch→picture latency, two fingers, text, rotation, Home, recording hand-over; it turns the system's pointer trace on for its measurements and restores it). `monkey` aborts on devices without hardware keys ("SYS_KEYS has no physical keys"): launch apps with `cmd package resolve-activity` + `am start -n`.
- Agents' tabs, handoffs and demonstrations (ADR-0017 §9) can be tried with no agent: send `{"op":"browser_call","thread_id":…,"tab":"<id or name>","command":{"action":"handoff","reason":"…","timeout_secs":600}}` over a scratch daemon's socket (it blocks until Continue), then launch the app on that home: its panel comes up on the tab with the card. `{"op":"page_handoff_done","id":…}` is Continue. Every agent browser command goes through `Core::browser_call(thread, tab, BrowserCommand)`; a new command that only reads must be added to `BrowserCommand::allowed_read_only` or read-only tabs refuse it. The `click:` dev hook closes the panel: use `all:click:x,y,ms++browser` to click in it.
- Agents' `device_*` tools (iOS simulators, Android emulators; ADR-0020) are `crates/loftd/src/mcp_devices.rs`: points are pixels of the agent's last `device_screenshot` (long side ≤ 1000 px), sent to the daemon as fractions of the screen. Test without Xcode or the SDK through `DaemonOptions::device_backends` with `loft_core::devices::fake::FakeBackend`s, whose `log()` holds everything they were sent (`agents_use_devices_through_the_mcp_bridge` in `crates/loftd/tests/workbench.rs`); a scratch daemon gets the same fakes with `AGENTLOFT_FAKE_DEVICES=1`. Tests pass `device_backends: Some(Vec::new())` so they never touch this computer's devices. The same tools are a command line, `agent-device` (`crates/loftd/src/device_cli.rs`, `agentloftd --home <home> device …`): the daemon writes `<home>/bin/agent-device` (and `.cmd` on Windows) at start and puts that folder first on every agent session's `PATH`, with the thread in `AGENTLOFT_THREAD_ID` (`McpBridge::install_cli`, `session_env` in `loft-core`). Both go through `mcp_devices::run`; the size of the thread's last screenshot of each device (what points are in) is kept in `<home>/run/device-pictures/<thread>.json`, so the two agree. Try it by hand on a scratch daemon with `AGENTLOFT_FAKE_DEVICES=1`: `target/debug/agentloftd --home <dir> device help`; its test is `agent_device_runs_the_device_tools_from_a_shell`.
- iOS simulators (`crates/loft-core/src/devices/ios.rs`, ADR-0020): `simctl` lists, boots (headless: never Simulator.app) and runs apps; a running device's screen and input come from a helper, `agentloftd simulator <udid> --developer-dir <xcode> [--set <dir>]` (`crates/loft-sim`), that talks to Xcode's private CoreSimulator/SimulatorKit (what it uses and how it was found is at the top of `loft-sim/src/helper/sim.rs`). The helper speaks `loft_sim::wire` on stdin/stdout, so it can be driven by hand. Other agents may be using the user's simulators: try things in a device set of your own (`xcrun simctl --set /private/tmp/<dir> create …`; a scratch daemon takes it from `AGENTLOFT_SIMULATOR_SET=<dir>`). Live test: `cargo test -p loftd --test ios_live -- --ignored --nocapture` (makes and deletes its own iPhone). Don't register for `SimScreen`'s `registerScreenCallbacksWithUUID:…`: it shut the device down. Blocks given to CoreSimulator need a signature (`RcBlock::with_encoding`), or it throws "Block is missing signature field". The framebuffer stays portrait when the device turns; `screenProperties.uiOrientation` says how the interface is drawn in it (`loft_sim::geometry`).
- Xcode 27 moved things the iOS backend reads: SimulatorKit is in `Xcode.app/Contents/SharedFrameworks` (was `Contents/Developer/Library/PrivateFrameworks`; `loft-sim` tries both), device types' screen sizes are in `capabilities.plist`'s `ScreenDimensionsCapability` (no longer `profile.plist`'s `mainScreen*`), Simulator.app is gone (Device Hub replaces it), and `defaults read` of a never-set key says "Could not find key" on iOS 27. Its Maps asks for contacts on first launch. Installing Xcode, accepting its license and `mas` installs all need the user's password.
- The iPhone Duo (Xcode 27.1+, its own runtime `iOS-27-2-iPhone19-4`, same version as the general iOS 27.2 one) folds through SpringBoard's display tool service: `devices/ios_fold.m` is compiled by the daemon with this Mac's Xcode and run in the device with `simctl spawn` (it needs the `com.apple.springboard.sbdisplay.service` entitlement linked into `__TEXT,__entitlements`). Screen 1 is the cover; the inner screen's ID comes from the device type's `capabilities.plist` (`displays`, `displayType = integrated`) and is passed to the helper as `--screen <id>`: on an ordinary iPhone screen 3 is CarPlay's, so never guess built-in screens from the running device. The helper shows whichever of them was drawn on last and isn't black. Live test: `live_an_iphone_duo` (skips without a Duo runtime). Turning a Duo's screen off with `simctl io … screenConfig` shut the whole device down. Folding smoothly: the fold program stays running per device (`fold --serve`, a position a line: starting one in the simulator takes over a second), and a fold overtaken by a newer one is dropped. As a Duo folds it blanks its screens and reports the new screen still turned the old one's way for up to ~3 s; the helper holds back a foldable's black pictures (`BLACK_HELD`) and, just after a switch, pictures turned otherwise than that screen last was (`TURN_SETTLES`), and hands the new screen's surface and turn to the pictures thread together (`switched_turn`). Every picture says which screen it is of (`DeviceFrame::on_cover`): one screen turned can have the other's shape. The 3D view moves the hinge at once on a click, shows a screen's last good picture while a fold settles (`FOLD_SETTLES`), and never rolls a foldable's model (only the picture turns on its screen). To judge smoothness, screenshot the window every ~0.1 s through a fold and tile the frames (`ffmpeg -i %03d.png -vf "crop=…,scale=172:-1,tile=12x4"`), and read SpringBoard's sweeps: `simctl spawn <udid> log show --predicate 'process == "SpringBoard" AND eventMessage CONTAINS "absoluteSweeping"'` (one per fold asked).
- iOS simulator settings and gestures (`devices/ios.rs`, `loft-sim/src/helper/`): appearance, text size and contrast go through `simctl ui` (it reads `content_size small` back as `Small`); Reduce Motion is `ReduceMotionEnabled` in `com.apple.Accessibility` (`simctl spawn <udid> defaults write …`, then `notifyutil -p com.apple.accessibility.reduce.motion.status` and `…cache.reduce.motion`); the simulator has no VoiceOver. The app in front is the `UIKitApplication:<bundle>` of `simctl spawn <udid> launchctl list` whose process (a process of this Mac) has `getpriority(PRIO_DARWIN_ROLE = 6) == 1` (focal UI); widget renderers get that role too, so only `simctl listapps` apps count, else SpringBoard. Several fingers: SimulatorKit's `IndigoHIDMessageForMouseNSEvent` takes a second point; more are extra `0xa0`-byte finger events (`more_fingers` in `sim.rs`, up to ten). Count what a page receives with a page on a `127.0.0.1` server opened in Safari (`event.touches.length`): the simulator shares this Mac's network. Accessibility frames come from `AXPTranslator` through `-[SimDevice sendAccessibilityRequestAsync:…]` (`helper/ax.rs`); a just-booted device has no app in front for it for a while. `simctl privacy … location` doesn't stop Maps' own location prompt: the live test (`live_settings_and_fingers`) taps through Maps' first-run screens.
- Handoff forks save an `ItemBody::ContextSummary` in the child's timeline, not a composer draft. The core includes it with the first ordinary message (retrying after failure), so it must survive restarts and stay separate from user-entered text.
- Every daemon answer, event and snapshot is one message (`MAX_FRAME_LEN`). Anything that grows with the user's data (diffs, file reads, tool output) needs a bound where it is made. An answer that is still too big fails its request (`conn::encode`); anything else too big ends the connection and the client reconnects. Before that, a 14 MB untracked page in a working-tree diff silently killed the window's connection: requests still ran in the daemon, nothing came back, and "Connected" stayed on.
- To see what the user's daemon answers, send read-only requests (`get_diff`, a thread subscription) over its socket (frames as in "Seeding"); never ones that change their data. An answer that never comes, on a connection still open, is the dead-connection symptom.
- Agent CLI updates (`crates/loft-core/src/agent_updates.rs`): `ProbeHarness` reports a newer release only when it can tell how the CLI was installed (npm/pnpm/bun global, Homebrew formula or cask, Claude Code's own installer and its `autoUpdatesChannel`), and compares against that channel: Homebrew casks trail npm, and comparing across channels is how other tools show "update available" for a current CLI. `UpdateHarness` runs that package manager (desktop only; refused to browsers). Only the real daemon asks the web (`DaemonOptions::check_agent_updates`); tests leave it off. Try it with a scratch home whose `[harness.codex] path` is a fake `…/lib/node_modules/@openai/codex/bin/codex.js` printing an old version, with a fake `bin/npm` beside it; `AGENTLOFT_DEV_TAB=agent:codex` opens its settings page and `update:codex` runs the update 4 s after launch (once the toast is up). Dev hooks act only when a thread is open, so give the scratch home a project and a thread first.
- Agents get the login shell's environment without `PWD` and `OLDPWD` (`loft_config::process_env`, `capture_login_env`). OpenCode's `opencode run` (titles, suggestions) takes its folder from `$PWD`, not its real working directory, and fails with `UnexpectedStatus: 500` when its background service can't read that folder (TCC-protected `~/Desktop`). Test an environment change by starting a scratch daemon from a folder under `~/Desktop`.
- New Lucide icons go in `AppIcons` in `crates/loft-ui/src/assets.rs`; an unlisted icon renders as a blank box.
- gpui-kit `Button` / `Switch` / dropdown buttons default to the arrow cursor; chain `.cursor_pointer()`. Everything clickable shows a hand.
- A hand-drawn control (a `div` with `on_click`) whose click calls `cx.stop_propagation()` also needs `.claims_press()` (`crates/loft-ui/src/press.rs`). The window's text selection starts on any press, even in blank space. Stopping propagation keeps the mouse-up from ending it, so it keeps following the pointer with no button held. gpui-kit's `Button` already claims its press. The drawn title bars zoom the window on a double-click that no control claimed, so any hand-drawn control in them needs `.claims_press()` too (`press::claimed`).
- The Device panel (`crates/loft-ui/src/panel/device.rs`, ADR-0020) streams a simulator or emulator like a browser tab: `Topic::Devices` for the list, `Topic::Device(id)` for one screen, frames acked with `PageFrameAck`, input as fractions of the picture. It watches only while drawn (`Seen`, as views do) and never subscribes to a device the list hasn't named: the daemon answers an unknown one with `Fatal`, which ends the connection. Try it with no Xcode or Android SDK: a scratch daemon started with `AGENTLOFT_FAKE_DEVICES=1` (the app's daemon inherits it) has `ios:FAKE-PHONE`, `android:Fake_Phone`, `android:Fake_Fold` and two plugged-in phones (`android:@FAKE-USB`, and `android:@FAKE-LOCKED`, unauthorized); `AGENTLOFT_DEV_TAB=device` opens the panel's list, `device:<id>` opens that device and starts it if stopped. When an agent uses a device and the panel isn't on it, the same `DeviceView` is drawn in a card floating over the conversation (`workspace/device_card.rs`, `set_floating`: screen only; its edges and corners resize it, the height following the device's shape); the toolbar's float button does the same. There is one Device tab per device (`panel/device_tabs.rs`): a pick in a tab's list or picker is a `DeviceEvent::Pick`, and the panel shows the tab already on that device instead; a Device tab is renamed by double-click or its menu. Each thread's tabs (device and name) are kept in the window's session (`ui-session.json`, `device_tabs`; the older single `devices` entry is read and migrated). The tools drawer (`panel/device_tools.rs`) shows only the settings in `DeviceSettings::supported` and always the values read back with `DeviceSettings` after each `DeviceSet` (location, permissions and pushes aren't read back: it says what was sent). Option-drag on the screen pinches, Option+Shift-drag pans with two fingers, a trackpad pinch is a two-finger pinch (`panel/device_touch.rs`, sent as `DeviceInput::Touches`). Hooks: `devicetab:<id>` (another tab on that device), `devicepick:<id>` (pick it in the tab shown), `devicetools` (open the drawer), `devicefloat`, `later:<ms>:<hook>` (a hook after a delay); `do:` steps take held keys (`alt+drag=…`, `alt+shift+press=…`) and `pinch=x,y,delta`. Opening the drawer in the very frame that first draws a device stalled the window, so `devicetools` waits a moment; drive anything else that must happen after launch with `later:`. A device's settings are asked for outside the store's update (`on_state` runs inside it; asking reads the store and panics). The fake draws its white dot only while a finger is down: test a touch with `do:` `press=`/`hold=`, screenshot, then `release=` (a `click=` leaves nothing to see). With `AGENTLOFT_LOG=info,loft_ui::panel::device=trace` the app logs every input it sends (`to the device`).
- The Device panel's 3D model (toolbar's 3D button; `crates/loft-ui/src/panel/device_model.rs`, a child module of `device.rs`) is drawn by `crates/loft-raster`, our own software renderer (no GPUI, so it runs in the browser too): `device.rs` there builds the phone, tablet, book and flip models and their fold geometry, `raster.rs` draws them and keeps, for each screen pixel, which point of the device's picture it shows (`Raster::hit`), so a press on the drawn screen is an exact touch; presses elsewhere turn the model. It is built at `opt-level = 3` even in debug builds (root `Cargo.toml`); `cargo test -p loft-raster frame_time -- --ignored --nocapture` times a panel-sized frame (about 4 ms at 1000×1500 on an M-series Mac). `AGENTLOFT_DEV_TAB=device3d:<id>@<yaw>,<pitch>[,<hinge>]` opens a device in 3D at that angle (degrees), folded to `hinge` if given; `AGENTLOFT_LOG=info,loft_ui::panel::device=debug` logs frame times. The fake foldable `android:Fake_Fold` (Pixel-Fold-like; the cover when Closed) tries postures, the hinge slider and pinching (`do:` `pinch=x,y,delta`; a `do:` hook closes the side panel, so put it first: `all:do:…++device3d:…`). A `do:` drag needs `wait=50` between its `hold=` steps: the model's drag listeners are registered when the next frame draws. Pick against the panel's current origin, not the one when the model was last drawn: the panel moves while the picture stays the same.
- A scratch home with real agent CLIs installed shows "update available" toasts over the top right of the window for about ten seconds after launch: `do:` clicks on the side panel's toolbar land on them. Wait them out (`wait=14000`) or screenshot first.
- `AGENTLOFT_DEV_TAB=settings:<section>@end` opens that settings page scrolled to its end (what is below the fold). `AGENTLOFT_DEV_CLICK=x,y,after_ms` then clicks in the settings window.
- `AGENTLOFT_DEV_TAB=click:…` also takes `move x,y,after_ms` steps (the pointer moves with no button held), e.g. to check that nothing is left selecting after a click.
- A view that takes keys for something else (a page, a device, a terminal) gets Tab only if it shadows gpui-kit Root's `tab`/`shift-tab` (move focus to the next control) with `KeyBinding::new("tab", NoAction, Some(<its key context>))`. GPUI matches bindings before `on_key_down` listeners, so without that the key never reaches the view. The same goes for any other key bound further up.
- A `drag_over` style can't recolour text (text is coloured at layout); show a drop hint with an svg and `group_drag_over`.
- A subagent's isolated worktree starts from `origin/main`, not the local `HEAD`: unpushed commits (and `press.rs`-style helpers they add) are missing there. Merge its files back with `git merge-file <ours> <base> <theirs>` per file, base being the worktree's `HEAD`.
- Looping animations go through `spinner::looping` / `Spinner`, not `with_animation(..).repeat()`, or the window redraws every display refresh.
- A new HTTPS call through `ureq` 3 must name its TLS provider in code (native-tls on macOS/Windows, rustls elsewhere) or it panics at the first request.
- Claude Code's `--prompt-suggestions` (a `prompt_suggestion` line after each result) backs off account-wide while its guesses go unused (`promptSuggestionUnusedStreak` in `~/.claude.json`) and has other gates of its own; in testing (2.1.322) it rarely answered. Next-message suggestions are asked for by the core instead (`crates/loft-core/src/suggestions.rs`, through `Core::ask_once`).
- Before building on a guess about AppKit, read it: `lldb -b -o 'target create <binary linking AppKit>' -o "disassemble -n '<method>'"`.

## Security rules the code relies on (review of 2026-11-18)

- Agentloft's MCP tools are allowed without asking in every permission mode, so they must never give an agent more than its thread's mode: a spawned thread or automation is capped at the caller's mode, and `ChangeSetting { from: Some(thread) }` lets an agent below full access change only what `agent_limits::harmless` lists (`crates/loft-core/src/agent_limits.rs`). A new agent-facing tool that starts something, changes what runs, or writes settings goes through the same checks.
- Below full access, those tools also read only the caller's project, threads it spawned or was spawned from, and threads the person @-mentioned in one of their own messages (`agent_limits::Readable`; pass `from` on `ListThreads`/`ReadThread`/`GetDiff`/`ThreadOutcome`). Whatever deletes or lasts beyond the turn is asked about in the thread first (`Core::ask_agent`, `Request::AgentApproval`; the bridge's `mcp::confirm`): a new tool of that kind must ask too. Full access is never limited or asked: its agent has a shell as the user.
- Agents' tabs open `file:` addresses only inside the thread's workspace and its captures folder unless the thread has full access (`DriveOptions::any_local_file`, `uploads::check_open`). A new way for an agent to load a local document goes through `may_open_file`.
- A project's `[worktree] setup` runs outside any sandbox: it is asked about in the thread (approval card) until the user allowed that very command for the project (`<home>/setup-approved.json`). Full-access threads aren't asked.
- Links from agents', repositories' or another computer's text go through `file_links::open_outside` (http, https, mailto only), never `cx.open_url` directly: `file:` and app schemes run programs.
- Folders in the temporary directory go through `loft_config::private_temp_dir` (on Linux `/tmp` is shared, and another account could plant the folder or a symlink). Agent CLIs never run with a shared folder as their working directory: they read project settings (MCP servers, plugins) from it.
- Document parsers run in the app (and in a browser tab): an allocation that fails aborts the whole app, which `catch_unwind` can't stop. Check sizes a file declares before handing it to a library that allocates by them (`sheets::check_xls`, `pdf::images_fit`).
- On Linux, a URL passed to `cx.open_url` is on `xdg-open`'s command line, which every account can read: links with a secret go through `settings::web::open_secret_link`.

## How the maintainer likes work done

- Small UI fixes: make the obvious change, get it in front of them within minutes, and say early what is slowing things down.
- Use the platform's own mechanism. If a second workaround is piling up in the same area, find the root cause instead.
- Finish what can be done before reporting. A final "not done" list should only hold things that really can't be done, each with the reason.
- Report faithfully: what changed, how it was checked, what wasn't.
